# ADR-0007: Invitation — токен-based приглашения с вычисляемым статусом

## Статус
Принято — 2026-07-13 (Этап 6: Users и Workspace)

## Контекст
Исходный API-дизайн (Этап 1, раздел 5.3) предполагал единственный эндпоинт
`POST /workspaces/{id}/invite` — немедленное добавление участника по email,
без отдельной сущности приглашения. ERD (раздел 4) не заводил таблицу
`invitations`.

ТЗ Этапа 6 явно потребовало полноценный жизненный цикл: создание
приглашения → проверка статуса (в т.ч. незарегистрированным человеком, без
авторизации) → принятие. Немедленное добавление участника (без токена) не
покрывает случай "пригласили того, у кого ещё нет аккаунта".

## Решение

**Новая сущность `Invitation`** (`workspace/model.py`): `workspace_id`,
`email`, `role`, `token` (crypto-random, `secrets.token_urlsafe(32)`),
`invited_by`, `accepted_at` (nullable), `expires_at`.

**Статус — не хранимая колонка, а вычисляемое свойство**
(`Invitation.status`, Python `@property`): `pending` / `accepted` /
`expired` выводятся из `accepted_at`/`expires_at` на момент чтения. Осознанно
не enum-колонка: хранимый статус потребовал бы фоновой job'ы, которая
периодически помечает протухшие приглашения `expired` — лишняя
подвижная часть ради того, что и так тривиально вычисляется на лету.
Единственное место, где логика продублирована на уровне SQL (не Python-property)
— `PostgresInvitationRepository.get_pending_for_email`, которому нужен
`WHERE`, а не post-hoc фильтрация в память.

**Прямое добавление vs приглашение** — два разных сценария под явно разными
эндпоинтами, не один универсальный:
- `POST /workspaces/{id}/members` — email уже зарегистрированного
  пользователя, добавление немедленное (без токена).
- `POST /workspaces/{id}/invitations` — работает и для незарегистрированных
  email; `GET /invitations/{token}` публичный (без авторизации — человек
  ещё может не иметь аккаунта); `POST /invitations/{token}/accept` требует
  авторизации и сверяет `current_user.email == invitation.email`.

**Email-доставка — extension point**, не реализована: токен возвращается
прямо в теле ответа `POST .../invitations` (см. `InvitationRead`), реальная
отправка требует Celery+SMTP, отложенных с Этапа 1 (Roadmap).

## Последствия
- Расхождение с ERD Этапа 1 — новая таблица, новая Alembic-миграция
  (`28fe033d807a_add_invitations`), обновлён `models_registry.py`.
- `InvitationRead` (для владельца/админов workspace) намеренно не включает
  `token` — только `InvitationPublicRead` (без авторизации, по прямому
  токену) отдаёт данные приглашения, и тоже без токена в теле (он и так
  уже известен вызывающему — это часть URL). Список приглашений в
  workspace не раскрывает чужие токены никому, кроме как через прямой URL,
  полученный по email.
- Пока нет email-доставки, тестовый/API-клиент должен получить токен
  каким-то другим способом — в проде это письмо, в тестах этого проекта
  (см. `tests/modules/test_invitations.py`) — прямое чтение из БД через
  тестовую сессию. Это специфика теста, не часть публичного API.
