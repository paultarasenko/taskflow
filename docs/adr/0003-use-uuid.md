# ADR-0003: UUID вместо auto-increment ID для первичных ключей

## Статус
Принято — 2026-07-07

## Контекст
Все основные сущности (users, workspaces, projects, tasks, comments) отдаются через публичный REST API. Нужно решить, какой тип использовать для первичных ключей.

## Решение
Используем **UUID (v4)** для всех первичных ключей вместо serial/auto-increment integer.

- Публичный ID не раскрывает бизнес-метрики (нельзя по `task_id=1042` оценить, сколько всего задач создано в системе, или перебором обойти чужие задачи, меняя число в URL).
- UUID можно сгенерировать на клиенте/в сервисе до записи в БД — упрощает пакетные операции и будущую интеграцию с очередями, где ID нужен до коммита транзакции.
- Не создаёт "узкого места" автоинкремента при потенциальном шардировании/репликации в будущем.

## Последствия
- Индексы по UUID немного тяжелее integer (больше места, чуть медленнее B-tree вставка) — для масштаба портфолио-проекта не критично; при реальном высоконагруженном проде рассматривался бы UUIDv7 (сортируемый по времени) как компромисс.
- Отладка руками (просмотр БД) чуть менее удобна, чем с короткими integer ID — компенсируется тем, что вся работа с БД идёт через ORM/repository, не руками в psql.
