# ADR-0008: WebSocket-аутентификация и ConnectionManager поверх Redis Pub/Sub

## Статус
Принято — 2026-07-21 (Этап 8: Realtime)

## Контекст
Контракт `WSS /ws/projects/{project_id}?token=<jwt>` был зафиксирован ещё на
Этапе 1 (раздел 5.10), но не реализован — только заглушки модуля `websocket`
(Этап 2). Требовалось решить три вещи, для которых обычный HTTP-паттерн
проекта (`Depends(get_current_user)` + `@app.exception_handler(AppError)`)
не подходит напрямую: (1) как аутентифицировать WS-хендшейк, (2) как
раздавать события конкретным клиентам, (3) как это масштабируется на
несколько инстансов API.

## Решение

**1. Аутентификация — вручную, не через `Depends()`.** Обработчик
`@app.exception_handler(AppError)` в `main.py` применяется только к HTTP-
запросам; WebSocket его не проходит — необработанное исключение внутри WS-
хендлера просто обрывает соединение без осмысленного кода закрытия.
`get_current_user_ws()` (`core/dependencies.py`) вызывается явно внутри
`websocket/router.py`, обёрнут в try/except, при ошибке —
`websocket.close(code=1008)` (RFC 6455 Policy Violation). Токен — query-
параметром, не заголовком (у WS handshake нет привычного REST-заголовка).

**2. `ConnectionManager`** (`websocket/connection_manager.py`) — единственный
экземпляр на процесс (не создаётся через `Depends()` каждый запрос, держит
живое состояние). Комната = `project_id`. На каждый проект с хотя бы одним
локальным WS-клиентом — ровно одна Redis pub/sub подписка, рассылающая всем
локальным клиентам этой комнаты; подписка создаётся лениво при первом
подключении и отменяется, когда уходит последний локальный клиент.
`publish()` всегда идёт через Redis, даже для локальной доставки — единый
код-путь независимо от того, сколько сейчас реплик API (горизонтальное
масштабирование без sticky sessions, как и было задумано в разделе 2.3).

**3. `session: DbSession` для WS — тот же `Depends(get_db_session)`, что и у
HTTP-роутов**, не отдельная сессия в обход DI. Это осознанный компромисс:
сессия держится на весь WS-хендлер (auth-проверка происходит один раз в
начале, дальше сессия не используется, но FastAPI не даёт освободить её
раньше конца хендлера без ручного управления жизненным циклом). Плата —
одно пуловое соединение на активное WS-соединение; для масштаба портфолио-
проекта это приемлемо, и что важнее — сохраняет тестируемость через
`app.dependency_overrides` (см. ниже).

**4. `notification.created` публикуется в комнату проекта, не персонально
пользователю.** WS-контракт (раздел 5.10) комнатный, не per-user —
`TaskService.assign_user`/`CommentService.create` публикуют это событие в
`project:{id}`, откуда его получат все, кто сейчас смотрит на доску этого
проекта. Известное ограничение: пользователь, не подключённый к комнате
конкретного проекта в момент события, не получит уведомление в реальном
времени (увидит только через `GET /notifications` при следующем заходе).
Per-user WS-канал не строился — не запрашивался и не входил в исходный
контракт раздела 5.10.

## Последствия
- `TaskService`/`CommentService` получили пятый/шестой конструкторный
  параметр (`ConnectionManager`) — консистентно с тем, как эти сервисы уже
  расширялись на Этапах 5–7 (см. историю PROJECT_STATE.md).
- Ошибка публикации в Redis не должна ронять бизнес-операцию: `_publish()`
  в обоих сервисах оборачивает `connection_manager.publish()` в try/except
  с логированием — задача/комментарий уже сохранены в БД к этому моменту,
  realtime-канал дополнительный, не источник истины.
- **Тестирование WebSocket потребовало отдельного открытия**: Starlette
  `TestClient` (единственный способ тестировать WS в этом стеке — у
  `httpx.AsyncClient` нет поддержки WS) запускает ASGI-приложение в
  отдельном потоке со своим event loop. Обычная транзакционная `db_session`
  (используемая всеми остальными тестами через `client`-фикстуру) не может
  быть использована из другого loop — при попытке упадёт с `RuntimeError:
  ... attached to a different loop`. Решение — отдельный `NullPool`-engine
  для WS-тестов (`tests/modules/test_websocket.py`): без кэша живых
  соединений между чекаутами каждый checkout создаётся заново в _текущем_
  loop и закрывается сразу по возврату, поэтому вопрос "из какого loop его
  закрывать" не возникает в принципе. Подробности и история отладки — в
  докстринге самого файла теста.
