# ADR-0006: Generic BaseRepository и session-per-request auto-commit

## Статус
Принято — 2026-07-09 (Этап 4: Database layer)

## Контекст
ADR-0004 зафиксировал Repository Pattern как единственную реальную границу
между сервисным слоем и SQLAlchemy, но не уточнял, как избежать дублирования
одного и того же кода (`get_by_id`, `list`, `add`, soft-delete-aware `delete`)
в 7 модулях, которые владеют моделями (users, workspace, projects, tasks,
comments, notifications, ai). Также требовалось решить, где именно
происходит `session.commit()` — в каждом сервисе отдельно, или один раз
на границе запроса.

## Решение

**1. `BaseRepository[ModelType]`** (`app/database/repository.py`) — общий
generic-класс с `get_by_id`, `list`, `add`, `delete`. Soft-delete определяется
через `hasattr(model, "deleted_at")` во время выполнения — не через отдельный
флаг или вторую иерархию классов: модели, у которых есть `deleted_at`
(Workspace, Project, Task), автоматически получают мягкое удаление и
фильтрацию `WHERE deleted_at IS NULL`; у остальных (User, Comment,
WorkspaceMember, association-таблицы) `delete()` делает настоящий SQL DELETE.
Конкретные репозитории модулей (`PostgresUserRepository` и т.д.) наследуют
этот класс и добавляют только доменные запросы (`get_by_email`,
`list_by_project` с фильтрами и т.п.).

**2. Session-per-request с auto-commit на границе запроса**
(`app/database/session.py: get_session()`) — FastAPI-зависимость коммитит
сессию один раз в конце запроса, если не было исключения, и откатывает при
любой ошибке. Сервисы вызывают `repository.add()` (который делает `flush()`,
но не `commit()`) и не обязаны помнить про коммит в каждом юзкейсе. Юзкейсам,
которым нужен более гранулярный контроль (промежуточный commit посреди
запроса), ничто не мешает сделать это явно — обвязка не перехватывает такие
вызовы.

## Последствия
- Новый модуль с моделью получает CRUD "бесплатно" — не переизобретает
  `SELECT ... WHERE id = :id` (см. docstring `BaseRepository`).
- Риск: `hasattr`-проверка на `deleted_at` — duck typing, не заявленный
  протокол; если модель случайно назовёт похожее поле иначе, soft delete
  для неё молча не сработает (упадёт в `else`-ветку настоящего DELETE).
  Мера предосторожности — `SoftDeleteMixin` (ADR/раздел 4.2) как
  единственный источник этого поля во всём проекте, а не ручное объявление
  `deleted_at` где попало.
- Один `commit()` на запрос означает, что если сервис вызывает несколько
  репозиториев в одном юзкейсе (например, создание задачи + запись в
  activity log), они атомарны в рамках одной транзакции без явного
  Unit-of-Work объекта — упрощение по сравнению с изначально заложенным в
  разделе 2.3 архитектурного документа отдельным UoW-классом, который на
  практике оказался не нужен при таком дизайне зависимостей.
