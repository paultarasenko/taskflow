# ADR-0004: Плоская модульная структура вместо 4-слойной Clean Architecture

## Статус
Принято — 2026-07-07 (пересмотрено по итогам Tech Lead review, см. `docs/architecture.md` v1.1)

## Контекст
Изначальный вариант архитектуры выделял четыре формальных слоя: Domain, Application, Interface Adapters, Infrastructure — классическая Clean Architecture / Onion Architecture. При ревью это было отмечено как избыточное для масштаба проекта: в Python такое разделение часто превращается в интерфейсы ради интерфейсов, а не в реальную защиту от смены технологий.

## Решение
Используем **плоскую модульную структуру**: `app/modules/{auth,users,workspace,projects,tasks,comments,notifications,ai,websocket}/`, внутри каждого модуля — `model.py, schema.py, repository.py, service.py, router.py`.

Единственная граница, которая реально работает — интерфейс репозитория (`Protocol`), достаточный для подмены реализации в тестах и защиты сервисного слоя от прямых SQLAlchemy-вызовов.

Точечное исключение: модуль `tasks` дополнительно получает `entity.py` — там есть настоящая бизнес-логика (переходы статуса, WIP-лимит, проверки прав на move), не сводимая к ORM-полям. Остальные модули — CRUD, где ORM-модель и есть доменная модель.

## Последствия
- Меньше файлов и меньше косвенности при чтении кода — быстрее онбординг.
- Если в будущем модуль (например, `workspace` с ростом биллинг-логики) обрастёт бизнес-правилами, для него по аналогии с `tasks` заводится свой `entity.py` — расширение делается точечно, а не переписыванием всего проекта под 4 слоя сразу.
- Осознанный компромисс: меньше "академической чистоты", больше поддерживаемости для команды/проекта такого размера.
