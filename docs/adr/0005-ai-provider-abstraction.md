# ADR-0005: Adapter Pattern для AI-провайдеров

## Статус
Принято — 2026-07-07

## Контекст
AI-функциональность (разбор текста на задачи, breakdown, summary) должна опираться на LLM. Провайдеров на рынке несколько (OpenAI, Anthropic, Google Gemini, OpenRouter), у каждого свой SDK и формат structured output. Нужно решить, встраивать ли конкретного провайдера напрямую в сервисный слой или закладывать абстракцию сразу.

## Решение
Вводим единый интерфейс **`AIProvider`** (`generate_subtasks()`, `summarize()`, `prioritize()`), возвращающий нормализованные Pydantic-схемы независимо от провайдера. `AIService` работает только с этим интерфейсом.

В Portfolio MVP реализована **только `OpenAIProvider`** — остальные (`AnthropicProvider`, `GeminiProvider`, `OpenRouterProvider`) в Roadmap. Ценность паттерна не зависит от количества реализаций: интерфейс и точка расширения зафиксированы сразу, второй провайдер добавляется без изменения вызывающего кода.

## Последствия
- `AIService` и роутеры не знают, какой именно LLM отвечает — тестируются через мок `AIProvider`, без реальных вызовов к API в CI (contract-тесты на фиксированных фикстурах).
- Риск: разные провайдеры по-разному обрабатывают structured output/function calling — при добавлении второго провайдера нормализация в `AIProvider.generate_subtasks()` должна быть проверена именно на границе адаптера, а не полагаться на то, что "AI всегда возвращает валидный JSON".
- Выбор провайдера — через конфиг (`AI_PROVIDER=openai`), фабрика в `core/dependencies.py` создаёт нужную реализацию.
